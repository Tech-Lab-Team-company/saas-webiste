توثيق تقني — Book Payment Flow

تم توحيد شراء الكتاب مع نظام دفع الكورس

شرح تفصيلي لمسار إنشاء جلسة الدفع، حفظ رقمها، الانتقال إلى بوابة الدفع، الرجوع منها، ثم التحقق من النتيجة عن طريق الـbackend.

1. الهدف من التعديل

كان شراء الكتاب يعتمد أساسًا على buy_product. أما دفع الكورس الإلكتروني فكان يمر بدورة دفع متكاملة تبدأ بإنشاء جلسة وتنتهي بالتحقق منها. تم تطبيق نفس الدورة على الكتاب مع الاحتفاظ بالحقول الخاصة بالكتاب وبيانات توصيل النسخة الورقية.

اختيار وسيلة الدفع← إنشاء جلسة الدفع← حفظ رقم الجلسة← فتح الـGateway← الرجوع والتحقق
  1. استدعاء create_payment_session.
  2. استقبال data.id وdata.url.
  3. حفظ رقم الجلسة وسياق المنتج مؤقتًا.
  4. تحويل الطالب إلى رابط بوابة الدفع.
  5. رجوع الطالب إلى /paymentverify/{paymentMethodId}.
  6. إرسال رقم الجلسة إلى verify_payment.
  7. عرض انتظار أو نجاح أو فشل.

3. معنى type في وسيلة الدفع

يتم تحميل وسائل الدفع من fetch_payment_methods. كل وسيلة تحتوي على id وtitle وtype وباقي بيانات العرض.

القيمة المعنى المسار
type = 1 بوابة دفع إلكترونية مثل Fawaterk create_payment_session ثم verify_payment
type = 2 تحويل يدوي مثل Instapay buy_product مع رقم التحويل والإيصال 
const isOnlinePayment = computed(
  () => Number(selectedMethod.value?.type) === 1,
)

const isOfflinePayment = computed(
  () => Number(selectedMethod.value?.type) === 2,
)
مهم: الذي يحدد مسار التنفيذ هو selectedMethod.type، وليس قيمة payment_method_id نفسها.

4. ما يحدث عند فتح نافذة الشراء

  1. يتم التأكد أن الطالب مسجل الدخول.
  2. إذا لم يكن مسجلًا، يظهر Toast ويتم تحويله إلى /loginhome مع حفظ الصفحة الحالية داخل query اسمه redirect.
  3. إذا كان مسجلًا، يتم تحميل وسائل الدفع باستخدام FetchPaymentMethodController.
  4. يتم تخزين وسائل الدفع في usePaymentStore.
  5. بعد اختيار الوسيلة، يتم استخراج الـmodel المطابق من خلال selectedPaymentMethodId. 
const selectedMethod = computed(() =>
  paymentMethods.value.find(
    (method) => method.id === selectedPaymentMethodId.value,
  ),
)

5. التحقق من البيانات

النسخة الورقية

عندما تكون requiresDelivery = true تصبح الحقول التالية مطلوبة:

  • city وaddress.
  • lat بين -90 و90.
  • lng بين -180 و180.
  • teacher_district.
  • location_details.

الدفع الإلكتروني

لا يُطلب إيصال؛ بوابة الدفع والـbackend هما المسؤولان عن إثبات النتيجة.

التحويل اليدوي

يجب إدخال transferred_account ورفع صورة receipt. يتم قبول الصور فقط وبحد أقصى 5MB.

6. الدفع الإلكتروني للكتاب — type = 1

إنشاء callback URL

const callbackUrl = buildSiteUrl(
  `/paymentverify/${selectedMethod.value.id}` +
  `?source=book&bookId=${props.bookId}`,
)

مثال للرابط الناتج:

https://example.com/paymentverify/3?source=book&bookId=17
  • 3 هو payment_method_id.
  • source=book يحدد أن العملية تخص كتابًا.
  • bookId=17 يساعد في بناء رابط الرجوع.

Payload إنشاء الجلسة

تم إنشاء BookOnlinePaymentParams لأن الكورس يرسل course_id بينما الكتاب يحتاج book_id وsubscription_type. 

{
  "book_id": 17,
  "subscription_type": 1,
  "payment_method_id": 3,
  "callback_url": "https://example.com/paymentverify/3?source=book&bookId=17",
  "success_url": "https://example.com/paymentverify/3?source=book&bookId=17",
  "back_url": "https://example.com/paymentverify/3?source=book&bookId=17",
  "fail_url": "https://example.com/paymentverify/3?source=book&bookId=17",
  "cancel_url": "https://example.com/paymentverify/3?source=book&bookId=17"
}

للنسخة الورقية تتم إضافة:

{
  "city": "القاهرة",
  "address": "شارع المثال، مبنى 10",
  "lat": 30.04442,
  "lng": 31.235712,
  "teacher_district": "مدينة نصر",
  "location_details": "الدور الثالث"
}

الطبقات التي يمر بها الطلب

BuyBookDialog← Controller← Use Case← Repository← API Service

الـAPI service يرسل طلب POST موثقًا إلى create_payment_session. الاستجابة المطلوبة تحتوي على: 

{
  "data": {
    "id": 9841,
    "url": "https://payment-gateway.example/session/..."
  }
}

id هو رقم جلسة الدفع، وurl هو رابط البوابة. لا يتم التحويل إذا كان أحدهما ناقصًا أو كان الـID غير صالح.

7. كيف تم حفظ رقم جلسة الدفع؟

بعد نجاح create_payment_session وقبل مغادرة الموقع يتم حفظ الرقم: 

window.localStorage.setItem(
  "onlinePaymentId",
  String(paymentId),
)

إذا رجع id = 9841 تصبح القيمة:

key: onlinePaymentId
value: "9841"

السبب هو أن الانتقال إلى بوابة خارجية يهدم صفحة Vue الحالية، وبالتالي تضيع قيم ref الموجودة في الذاكرة. نحتاج الرقم مجددًا عند رجوع الطالب.

حفظ سياق المنتج

window.localStorage.setItem(
  "onlinePaymentContext",
  JSON.stringify({
    source: "book",
    bookId: props.bookId,
    title: props.title,
    optionLabel: props.optionLabel,
    returnUrl: route.fullPath,
  }),
)
القيمة وظيفتها
source تمييز الكتاب عن الكورس.
bookId بناء fallback لرابط الرجوع.
title عرض اسم الكتاب في نتيجة الدفع.
optionLabel عرض نوع النسخة.
returnUrl إعادة الطالب للصفحة التي بدأ منها.
تنبيه: الـLocal Storage ليس إثباتًا لنجاح الدفع. هو مجرد وسيلة لاستكمال الرحلة، ومصدر الحقيقة هو verify_payment.

بعد الحفظ يتم فتح البوابة:

visible.value = false
window.location.assign(gatewayUrl)

8. الرجوع من بوابة الدفع

البوابة تعيد الطالب إلى:

/paymentverify/[payment_method_id]

الصفحة pages/paymentverify/[id].vue تعرض PaymentVerify. عند mount يتم: 

onMounted(() => {
  readPaymentContext()
  verifyPayment()
})

يتم قراءة onlinePaymentContext داخل try/catch حتى لا تتعطل الصفحة إذا كانت القيمة مفقودة أو غير صالحة.

كيف نعرف أن العملية تخص كتابًا؟

const isBookPayment = computed(() =>
  route.query.source === "book" ||
  paymentContext.value.source === "book",
)

9. استخراج الأرقام واستدعاء verify_payment

الرقم مصدره وظيفته
payment_method_id route.params.id تعريف وسيلة الدفع.
payment_id استجابة إنشاء الجلسة تعريف جلسة الدفع المحددة.

تبحث شاشة التحقق عن payment_id بهذا الترتيب:

  1. payment_id داخل query العائدة من البوابة.
  2. paymentId لدعم تسمية بديلة.
  3. onlinePaymentId من Local Storage كـfallback.
const paymentMethodId = Number(route.params.id)

const returnedPaymentId = Array.isArray(route.query.payment_id)
  ? route.query.payment_id[0]
  : route.query.payment_id || route.query.paymentId

const paymentId = Number(
  returnedPaymentId ||
  window.localStorage.getItem("onlinePaymentId"),
)

بعد validation يتم إنشاء payload:

{
  "payment_method_id": 3,
  "payment_id": 9841
}

ثم يمر الطلب عبر:

PaymentVerify← Verify Controller← Use Case← Repository← POST verify_payment

10. حالات الدفع

export enum PaymentVerifyEnum {
  PENDING = 1,
  SUCCESS = 2,
  FAILED = 3,
}

PENDING = 1

  • العملية وصلت لكنها لم تُحسم.
  • يظهر زر إعادة التحقق.
  • لا يتم حذف رقم الجلسة.

SUCCESS = 2

  • تظهر رسالة نجاح مناسبة للكتاب أو الكورس.
  • يتم حذف بيانات العملية المؤقتة.

FAILED = 3

  • تظهر رسالة أن الدفع غير مكتمل.
  • يتم حذف البيانات لأنها حالة نهائية.
if (
  paymentStatus.value === PaymentVerifyEnum.SUCCESS ||
  paymentStatus.value === PaymentVerifyEnum.FAILED
) {
  localStorage.removeItem("onlinePaymentId")
  localStorage.removeItem("onlinePaymentContext")
}

عدم الحذف أثناء PENDING أو خطأ الشبكة يسمح للطالب باستخدام «إعادة التحقق».

11. الرجوع إلى المنتج بأمان

يتم استخدام returnUrl فقط إذا كان مسارًا داخليًا يبدأ بـ/ ولا يبدأ بـ//. هذا يمنع Open Redirect إلى موقع خارجي.

  • Fallback الكتاب: /books/{bookId} ثم /books.
  • Fallback الكورس: /course/{courseId} ثم /course.

12. التحويل اليدوي — type = 2

هذا المسار لا يستخدم جلسة Gateway؛ يتم إرسال إثبات التحويل للمراجعة: 

{
  "book_id": 17,
  "subscription_type": 1,
  "payment_method_id": 8,
  "transferred_account": "01000000000",
  "receipt": "[File]"
}

يُرسل الطلب كـFormData إلى:

POST /api/website/v3/buy_product

للنسخة الورقية تضاف بيانات التوصيل. نجاح الطلب يعني إرسال الطلب للمراجعة، وليس تأكيد التحويل ماليًا.

13. مسار الانضمام

يوجد mode باسم join يرسل:

{
  "book_id": 17,
  "subscription_type": 5
}

ولا يرسل وسيلة دفع أو إيصال، مع إضافة بيانات التوصيل إذا كانت مطلوبة.

15. طريقة الاختبار من DevTools

اختبار type = 1

  1. سجل الدخول وافتح صفحة كتاب.
  2. اختر وسيلة قيمة type الخاصة بها تساوي 1.
  3. من Network راقب create_payment_session.
  4. تأكد من إرسال book_id وpayment_method_id وروابط callback.
  5. تأكد أن الرد يحتوي على data.id وdata.url.
  6. من Application → Local Storage راجع onlinePaymentId وonlinePaymentContext.
  7. بعد الرجوع راقب طلب verify_payment.
  8. تأكد أن payment_id يساوي ID جلسة الإنشاء.

اختبار type = 2

  1. تأكد من ظهور رقم الحساب وحقل الإيصال.
  2. اختبر validation دون صورة، ثم بصورة أكبر من 5MB.
  3. أرسل صورة صحيحة.
  4. تأكد أن buy_product أُرسل كـmultipart/form-data.
  5. تأكد من عدم استدعاء create_payment_session.

16. ملاحظات الأمان

  1. لا يتم تخزين بيانات بطاقة أو OTP داخل Local Storage.
  2. رقم الجلسة المخزن لا يثبت نجاح العملية.
  3. الـbackend يجب أن يتأكد أن الجلسة تخص الطالب والمنتج.
  4. يفضل استخدام webhook من البوابة إلى الـbackend حتى يتم تحديث الطلب إذا أغلق الطالب المتصفح.
  5. يجب تسجيل callback URLs في قائمة النطاقات الموثوقة لدى بوابة الدفع.
  6. المسار الداخلي للرجوع يتم التحقق منه لمنع Open Redirect.

17. الخلاصة التنفيذية

الدفع الإلكتروني: type 1 → create_payment_session → save data.id → open data.url → callback → verify_payment
التحويل اليدوي: type 2 → transferred_account + receipt → FormData → buy_product
توثيق مسار دفع الكتاب — مكتوب بترميز UTF-8 واتجاه RTL، مع عزل الأكواد التقنية باتجاه LTR.
